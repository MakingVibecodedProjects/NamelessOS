# PROMPT_32 — Phase 8 Step 3: Init Launch + Scheduler Stability

**Session date:** 2026-03-29
**Status when starting:** Phase 8 Step 2 complete (TTY, /dev/tty0, cooked mode)
**Status when done:** Phase 8 Step 3 complete — init ELF embedded, loaded into new PML4, iretq to userspace PID 1; shell forks and execs; scheduler freeze on command reuse fixed

## What was built

### `src/init_launch/` — new module
- `init_launch_internal.h` — `USTACK_TOP=0x7FFFF000`, `USTACK_PAGES=4`, `USER_RFLAGS=0x202`
- `init_launch.h` — `mod_init_launch` extern
- `init_launch_entry.asm` — `init_iretq_trampoline`: zeroes all GPRs, executes `iretq` into userspace; `.note.GNU-stack` at end
- `init_elf.c` / `shell_elf.c` — generated by `make userspace` via `xxd -i`; embed init and shell ELF binaries as C byte arrays
- `init_launch.c`:
  - Opens `/dev/tty0` three times → fds 0/1/2 (stdin/stdout/stderr)
  - `vmm_create_user_pml4()` — fresh user address space
  - `elf_load(init_elf_data, ..., pml4_phys, &entry)` — maps PT_LOAD segments into user PML4
  - `alloc_user_stack()` — allocates `USTACK_PAGES` frames, maps them at `0x7FFFE000..0x7FFFF000` with `PTE_USER|PTE_WRITE`
  - Allocates two PMM frames for kernel stack (`kstack_frame0`, `kstack_frame1`), builds iretq frame at top: SS, user-RSP, RFLAGS, CS, RIP
  - Maps kstack frames into user PML4 at their physical address (identity, kernel-only, `PTE_NX`) so ring-0 exception handlers can reach them under user CR3
  - `kthread_create("init", init_iretq_trampoline)` → overrides kstack/pml4/ctx; `gdt_set_tss_rsp0`, `syscall_set_kernel_rsp`
  - `scheduler_add(p)` — enqueues PID 1

### `src/syscall/syscall.c` — `sys_execve`
- Recognizes `/bin/shell`; loads embedded `shell_elf_data` into a new PML4
- Maps fresh user stack, switches CR3, builds iretq frame on new kernel stack, executes `iretq` into shell entry point
- Uses `kmalloc(KSTACK_SIZE)` for new kernel stack (lives in higher-half, accessible from every PML4)

### `src/scheduler/scheduler.asm` — CR3 switch fix
- Added `rdx = new_pml4` third argument
- CR3 write moved AFTER `mov rsp, [rsi+48]` — stack is on new process's kernel stack before address space changes; boot stack identity map (PML4[0]) is absent in user PML4s

### `src/scheduler/scheduler.c` — `scheduler_remove` + queue freeze fix
- Added `scheduler_remove(process_t *p)`: walks circular list to unlink `p`; handles single-element case; sets `p->next = NULL`
- Called from `process_waitpid` when reaping a ZOMBIE, before marking slot UNUSED — prevents stale circular-list nodes surviving pid slot reuse

### `src/process/process.c`
- `ctx.rsp = stack_top - 8` for both `kthread_create` and `process_fork` (was `-16`; fresh contexts are restored as-is, not via `rsp+8` save path)
- `process_waitpid`: calls `scheduler_remove(child)` before `child->state = PROC_UNUSED`

### `boot/entry.asm` — extended `pdpt_hh`
- Added pdpt_hh entries 508–511 (was only 510–511):
  - `pdpt_hh[508]` → phys `0x80000000` (VA `0xFFFFFFFF00000000`)
  - `pdpt_hh[509]` → phys `0xC0000000` (VA `0xFFFFFFFF40000000`) — covers e1000 MMIO at `0xfeb80000`
  - `pdpt_hh[510]` → phys `0x00000000` (VA `0xFFFFFFFF80000000`) — kernel text/data
  - `pdpt_hh[511]` → phys `0x40000000` (VA `0xFFFFFFFFC0000000`)

### `src/net/e1000/e1000.c` — MMIO VA fix
- Changed MMIO access from raw physical address to higher-half VA:
  `mmio_va = 0xFFFFFFFF40000000ULL + (mmio_phys - 0xC0000000ULL)`
- This VA is in PML4[511] (kernel half), present in every PML4

### `userspace/programs/shell/shell.c`
- Changed em dash `—` (UTF-8, 3 bytes) to ASCII `-` in banner — VGA renders each byte as CP437

### `Makefile`
- Added `run-gui` target: `$(QEMU) ... -display sdl` — opens SDL window for keyboard input

### Debug logs stripped from hot paths
- `keyboard_irq_handler`, `tty_poll`, `vfs_write/fd_write`, `sys_write/fork/execve/waitpid/getpid`, `vmm COW resolved` — all removed to prevent scheduler starvation

## Key decisions

- **CR3 switch in asm, after RSP swap** — scheduler.c no longer calls `vmm_switch_to`; passes `new_pml4` as third arg to `context_switch`; the asm switches RSP first, then writes CR3; this closes the window where boot stack was mapped only via PML4[0] (absent in user PML4s)
- **e1000 MMIO in kernel half, not identity** — failed approach was copying PML4[0] into user PML4s; that caused a GPF when `vmm_map_user_page` walked a 1GB PS entry as a normal PDPT for addresses in `0x7FFF...` range; correct fix was extending pdpt_hh to cover the physical range containing the MMIO BAR
- **`scheduler_remove` on waitpid reap** — ZOMBIE processes stay in queue until reaped (fine), but must be removed before slot is reused; without this, the second fork of pid3 inserts pid3 again while old pid3's `next` pointer still links in the queue, creating a double-link loop that deadlocks the scheduler

## Known traps discovered

- **Circular run queue freeze on pid slot reuse** — `process_waitpid` set `child->state = PROC_UNUSED` without removing the node from the run queue; next `alloc_pid` reused the slot and called `scheduler_add` inserting it again; old `next` pointer created a malformed circular list causing infinite looping or deadlock; fix: call `scheduler_remove(child)` before marking UNUSED
- **e1000 MMIO page fault under user PML4** — MMIO at physical `0xfeb80000` was accessed via PML4[0] identity map which user PML4s don't have; copying PML4[0] into user PML4s hit a GPF because user stack VA `0x7FFF...` is in the same PML4[0] range and `vmm_map_user_page` walked the 1GB PS entry as a normal table; real fix: extend pdpt_hh to cover physical `0xC0000000–0xFFFFFFFF` at a kernel-half VA
- **CR3 switch on boot stack = bootloop** — scheduler called `vmm_switch_to(user_pml4)` while still on boot stack (VA in PML4[0]); user PML4 has no PML4[0]; `ret` from `vmm_switch_to` jumped to unmapped address; fix: move CR3 write into context_switch.asm after RSP is already on new kernel stack
